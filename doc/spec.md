# Network sandbox — specification

A minimal allowlisting HTTP proxy for Windows. It listens on loopback only, forwards traffic to whitelisted destinations, logs every decision, and denies everything else.

## 1. Purpose and scope

Limit web and network access for AI agents. The proxy is one layer of three:

1. The agent runs as a restricted Windows user.
2. Firewall rules allow that user loopback traffic only.
3. This proxy forwards only whitelisted requests to the outside.

Without the proxy, the agent has no network. With it, the agent reaches only the whitelisted `host:port` pairs (§5 and §9 state what that covers).

Inspired by [GO Simple Tunnel](https://github.com/go-gost/gost), but as simple as possible.

## 2. Decisions

| Topic | Decision | Rationale |
|---|---|---|
| Protocol | HTTP proxy: `CONNECT` tunnels plus plain-HTTP forwarding | Tools honor `HTTPS_PROXY`/`HTTP_PROXY` (Claude Code, curl, git, npm, pip). No SOCKS. |
| Matching | Exact `host:port` and `*.domain:port` wildcards | Services like GitHub span many subdomains. |
| Language | Go, single static `.exe` | No runtime, `net/http` covers proxying, small codebase. |
| Config reload | Read once at startup; restart to apply changes | No state that changes mid-session. |
| TLS | The proxy never terminates or originates TLS and holds no certificates | `CONNECT` tunnels pass TLS through untouched, so upstream TLS inspection (e.g. FortiGate) works as long as the clients trust the inspection CA (§8). |
| Admin rights | Not required | Binding `127.0.0.1` on a port above 1024 needs no privileges, and loopback-only listeners trigger no firewall prompt. |

## 3. Client interface

- Listens on `127.0.0.1:<port>` only. Only the port is configurable.
- `CONNECT host:port`: check the whitelist → dial the target → reply `200 Connection established` → copy bytes in both directions until either side closes or the tunnel is idle for too long (§7).
- Plain HTTP with an absolute URI (`GET http://host[:port]/path`): check `host:port` (default port 80) → forward the request. Strip hop-by-hop headers and `Proxy-*` headers.
- Responses generated by the proxy:

  | Case | Status | Body |
  |---|---|---|
  | Target not whitelisted | `403` | `network-sandbox: <host:port> not in whitelist` |
  | Hostname resolves to a non-public address (§5) | `403` | `network-sandbox: <host:port> resolves to a non-public address` |
  | Not a proxy request (origin-form, e.g. `GET /`) | `400` | short reason |
  | Upstream dial or forward failure | `502` | short reason |

  The text bodies tell the agent why a request failed.

- Agents use the proxy by setting:

  ```
  HTTPS_PROXY=http://127.0.0.1:8080
  HTTP_PROXY=http://127.0.0.1:8080
  ```

## 4. Config file

INI format. Default path: `network-sandbox.ini` next to the executable.

If the config file doesn't exist, the proxy writes the example below to that path and exits with a nonzero code instead of starting. It never starts with a whitelist nobody has reviewed, and it never overwrites an existing file.

```ini
[network-sandbox]
port=8080                      # required, 1-65535
logfile=network-sandbox.log    # optional; relative paths resolve next to the exe
loglevel=info                  # optional: error | warn | info | debug
privateaddresses=deny          # optional: deny | allow - whether whitelisted hostnames may resolve
                               # to loopback, private or link-local addresses

[whitelist]
# Claude
api.anthropic.com:443
claude.ai:443
platform.claude.com:443
downloads.claude.ai:443
# Microsoft
microsoft.com:443
# GitHub
github.com:443
*.githubusercontent.com:443
```

Syntax:

- Two sections: `[network-sandbox]` and `[whitelist]`. Section and key names are case-insensitive.
- `#` or `;` start a comment, either on its own line or after whitespace at the end of a line. Blank lines are ignored.
- `[whitelist]` holds one entry per line:

  | Form | Example | Matches |
  |---|---|---|
  | Host | `github.com:443` | `github.com:443` only |
  | Wildcard | `*.githubusercontent.com:443` | any subdomain at any depth, e.g. `raw.githubusercontent.com:443`; **not** the apex `githubusercontent.com` |
  | IPv4 | `140.82.112.3:443` | that literal IP |
  | IPv6 | `[2001:db8::1]:443` | that literal IP |

- The port is required and must be a single number. Port wildcards and ranges aren't supported.
- `*` is allowed only as a whole leading label (`*.`), never elsewhere.

Validation fails closed. Any of the following prints an error to stderr and exits with a nonzero code:

- missing or invalid `port`, or an invalid value of another key
- unknown section or key
- malformed whitelist entry
- empty whitelist
- log file that can't be opened

## 5. Matching and security rules

- Match the host string the client *requested*, never the IP it resolves to. The proxy resolves DNS through the system resolver, so the agent needs no DNS access.
- A hostname entry connects to public addresses only: not loopback, private (RFC 1918, unique local), link-local, carrier-grade NAT, multicast or reserved addresses. Otherwise a DNS answer could point an allowed name at the proxy's machine or the local network. The check applies to the address of each connection attempt, so a name that resolves differently the next time (DNS rebinding) can't pass it. A failed check is logged as `deny` with the error. `privateaddresses=allow` turns the check off for all hostname entries, for networks with internal hosts.
- An IP entry names its address explicitly and is connected as written, public or not.
- Normalize before matching: lowercase, and strip one trailing dot.
- An IP-literal request matches IP entries only. A hostname request never matches IP entries.
- Everything not matched is denied, including `localhost`, `127.0.0.1`, and the proxy's own port.

## 6. Logging

- In console mode, logs go to both stdout and the configured log file.
- One line per plain-HTTP request or `CONNECT` tunnel, in Go `log/slog` text (key=value) format.
- Fields: `time` (RFC 3339), `client`, `method`, `target` (`host:port`), `decision` (`allow`/`deny`), `status`, `bytes_up`, `bytes_down`, `duration`, `error` (if any).
- Tunnels are logged when they close, so byte counts and duration are final.
- Levels:
  - `info` (default): every allow/deny decision plus startup and shutdown.
  - `debug`: also the URL and headers of plain-HTTP requests. The URL is logged without user information, and its query string is replaced by `[redacted]`. Header values are redacted except those of `Accept`, `Accept-Encoding`, `Content-Length`, `Content-Type` and `User-Agent`: credentials travel in too many headers to list them. `CONNECT` traffic is opaque.
  - `warn` and `error`: proxy-internal problems only.
- The file is opened in append mode. When a line would grow it beyond 10 MB, it is renamed to `<logfile>.1`, the previous files move up to `.2` and `.3`, and the oldest is deleted. This bounds the log at 40 MB, because a client controls how much is logged. If the file can't be renamed, e.g. because another program holds it open, it is truncated instead. Configs must not share a log file.

## 7. Operation

- CLI: `network-sandbox.exe [start|stop|restart|status] [-config <path>]`.
- `-help`, `-?`, `/?`, `/help` (also `-h`, `--help`, case-insensitive, anywhere on the command line) print usage and exit 0. Invalid arguments print a short hint to `-help` and exit 2.
- Without a command, it runs in the console. At startup it logs the listen address and the number of whitelist entries. Ctrl+C stops accepting connections, closes open tunnels, and exits.
- Background mode, without installing a Windows service:

  | Command | Behavior |
  |---|---|
  | `start` | Checks the config, log file and port, then starts a detached copy of itself without a console. Waits until that process listens on the port, and writes its PID and creation time to the PID file. Fails if it's already running. |
  | `stop` | Terminates the process that the PID file identifies and deletes the file. Open connections are cut. Succeeds if nothing is running. |
  | `restart` | `stop`, then `start`, as one step. Use it to apply config changes. |
  | `status` | Without `-config`: lists every running proxy as `running (pid <pid>) on <listen address> -config <path>`. It reads the process list, so it includes proxies that run in a console. Exits with 0 if any runs, or 3 if none. With `-config`: prints the same line for that config's background proxy, found through its PID file, and exits with 0 if it runs, or 3 if not. |

  Each config has its own PID file and so its own background proxy; `start`, `stop` and `restart` act on the proxy of the given config (by default `network-sandbox.ini` next to the executable). The PID file is the config path plus `.pid`, e.g. `network-sandbox.ini.pid`, so two configs never share one and it never coincides with a config.

  `start`, `stop` and `restart` of the same config run one at a time. They hold `<config>.pid.lock` open while they run; a command that can't get it within 30 s fails.

  A process counts as a running proxy if it was started from an executable named like this one and listens on a `127.0.0.1` TCP port. The name alone isn't enough: it also matches unrelated programs and `network-sandbox` commands in progress. A PID alone can be reused by another process, so the PID file also holds the creation time of the process: the file counts only if a process with that PID and creation time is still running and passes the check above. `stop` terminates through the same process handle that it checked. Checking the process requires access to it; for a proxy of another account, `status -config` and `stop` fail with an error unless run with sufficient rights.

  The listed config is the proxy's own `-config` argument as it was given, or the default config next to its executable if it was started without one. For a proxy that belongs to another account the arguments can't be read, and the line ends after the listen address.

  There is no network control endpoint, because the agent could use it to stop the proxy. `stop` needs the rights to terminate the process, so the agent user can't stop a proxy that runs under another account.
- Timeouts:
  - dial: 10 s
  - reading request headers: 30 s
  - client connection between two requests: 2 min
  - tunnel, request or response without traffic in either direction: 15 min. Traffic in one direction keeps the other open.
- Limits: the agent must not be able to exhaust the proxy, which runs outside its account. The proxy serves at most 256 client connections at a time; further clients wait in the listen backlog. Together with the timeouts and the log size (§6), this bounds the memory, sockets and disk space a client can use. The limits are fixed.

## 8. Deployment notes

These are outside the tool's code, but the setup depends on them:

- Run the proxy as a different user than the agent, one that is allowed outbound traffic.
- Set ACLs so the agent user can't modify or delete the executable, config, or log files, and can't create files in the config's directory. That directory holds the PID file, which decides what `stop` terminates.
- Firewall rules that restrict the agent user to loopback are configured separately.

### TLS inspection (FortiGate)

On networks with transparent TLS inspection, the FortiGate re-signs every server certificate with the company CA. The TLS handshake runs between the client tool and the FortiGate, through the proxy's tunnel, so the **agent user's tools** must trust the company CA. The proxy needs no configuration for this.

Tools that use the Windows certificate store work once the CA is in the agent user's trust store. If company policy already deploys it to `LocalMachine\Root`, nothing more is needed. Otherwise import it for the agent user:

```powershell
Import-Certificate -FilePath company-ca.cer -CertStoreLocation Cert:\CurrentUser\Root
```

This covers PowerShell, .NET, curl.exe (Schannel), and git with `http.sslBackend=schannel`.

Tools with their own CA bundle need the CA as a PEM file, set in the agent's environment:

| Tool | Setting |
|---|---|
| Node.js (Claude Code, npm) | `NODE_EXTRA_CA_CERTS=C:\path\company-ca.pem` |
| Python (pip, requests) | `REQUESTS_CA_BUNDLE`, `PIP_CERT` or `SSL_CERT_FILE` pointing to a bundle that includes the CA |
| git with the OpenSSL backend | `git config --global http.sslCAInfo C:\path\company-ca.pem`, or switch to Schannel |

Errors like `self-signed certificate in certificate chain` or `unable to get local issuer certificate` mean the client is missing the CA. They are not a proxy failure.

Whitelist matching is unaffected, because the proxy matches the `CONNECT` target before any TLS starts.

## 9. Non-goals and known limits

- **The proxy does no TLS inspection of its own.** For HTTPS only `host:port` is controlled and logged. Paths and bodies aren't visible. Neither is the TLS server name (SNI) or the HTTP `Host` inside a tunnel: where several sites share servers, such as a CDN, a tunnel to an allowed host can ask those servers for another site.
- **An allowed hostname means whatever DNS answers**, limited to public addresses (§5). The proxy doesn't pin addresses or validate DNS.
- **The limits protect the proxy, not its availability to the agent.** A local process can use up all connections, or flood the log until older entries rotate out.
- **Whitelisted hosts can still carry data out**, e.g. pushing to GitHub.
- **DNS exfiltration** through the Windows DNS Client service isn't covered by this tool.
- **No authentication.** Any local process can use the proxy, which only grants whitelisted access anyway.
- Not in v1: SOCKS, UDP, hot reload, running as a Windows service.

## 10. Acceptance criteria

**Unit tests**

- Config parsing: valid files, plus each failure case from §4.
- Matching table:
  - exact host
  - wildcard subdomain, including multi-level subdomains
  - wildcard vs apex
  - uppercase input
  - trailing dot
  - IP literal vs hostname entry, and hostname vs IP entry
  - port mismatch

**Integration tests.** Start the proxy on a random port, with a whitelist that points to a local `httptest` server, and check that:

- allowed `CONNECT` and plain-HTTP requests succeed
- non-whitelisted targets return `403` with the documented body
- origin-form requests return `400`
- log lines are written with the documented fields, and debug lines hold no credentials
- a whitelisted hostname that resolves to loopback returns `403`, unless `privateaddresses=allow`
- idle tunnels and stalled transfers are closed, while one-way traffic keeps a tunnel open
- connections beyond the limit wait, and the log rotates within its bound
- concurrent `start` commands start one proxy
- an invalid config exits nonzero

**Manual end-to-end check**

```
curl -x http://127.0.0.1:8080 https://api.anthropic.com   # gets a response from the upstream server
curl -x http://127.0.0.1:8080 https://example.com         # 403 from proxy
```

On the company network, run the first command as the agent user without `-k`, and start Claude Code with `NODE_EXTRA_CA_CERTS` set. Both must succeed through the FortiGate inspection.
